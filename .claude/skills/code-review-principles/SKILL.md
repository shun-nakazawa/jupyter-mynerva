# コードレビュー原則

実装・機能追加・リファクタリング時に以下の原則に従う。

## 基本原則

1. **差分最小化**: 必要な変更のみ行う。コスメティックな変数抽出やフォーマット変更は不要
2. **一貫性**: 既存の類似パターンに合わせる。例えばアクションタイプの追加時は既存のアクション（`getToc`, `getSection` 等）の実装パターンを踏襲する
3. **冗長な状態の排除**: データを重複させない。一度しか使わない変数はインライン化する
4. **シンプルな条件分岐**: 重複する分岐を統合する。共通コードは分岐の外に出す
5. **ログの粒度**: エラーとワーニングのみ記録する。デバッグログは通常フローに入れない。既存パターンに合わせる
6. **コメントの粒度**: 自明なコードにコメントしない。意図や理由のみコメントする。既存パターンに合わせる

## レビューチェックポイント

1. 各関数の詳細ロジック
2. 全体のデータフローと状態管理の効率性
3. 既存パターンとの一貫性

## 削除対象

- デッドコード（未使用の関数・変数）
- 到達不能な分岐、冗長な条件
- 重複コード

## プロジェクト固有ルール

- TypeScript は strict モード。`any` の使用を避ける
- フロントエンドは React 関数コンポーネント + Hooks パターン
- バックエンド（Python）は Tornado ハンドラパターン（jupyter_server ベース）
- デバッグコードや `console.log` はコミット前に削除
- エラーは明示的に throw する（暗黙のデフォルト値で握りつぶさない）
